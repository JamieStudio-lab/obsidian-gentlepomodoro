## Project Summary

**Gentle Pomodoro** is an Obsidian plugin: a soothing, task-integrated Pomodoro timer that links sessions to Tasks-plugin markdown items and writes Dataview-compatible daily logs. Currently **v0.5.7 (beta)**.

**0.5.7 added:** **up to three music links with an in-panel picker** (user request: add/delete/edit and choose from 1–3 URLs). Shape, and the reasoning behind it: **three FIXED scalar slots, not an array** — `musicUrl` (unchanged meaning = slot 1) plus `musicUrl2`/`musicUrl3`, `""` = empty. Pasting into an empty slot is "add", clearing one is "delete", typing over one is "edit", so the user capability is identical to a list while the failure surface is not: a variable-length array would have brought the shared-mutable-`DEFAULT_SETTINGS` hazard (the shallow `Object.assign` in `loadSettings` copies an array **by reference**, so an in-place push corrupts the module default for the life of the process — hence `musicPositions` is `Object.freeze([])` in [constants.ts](constants.ts), turning that silent corruption into a TypeError), index-shift-on-delete, id minting/reuse, synthesized keys falling through `setControlValue`'s silent `default: return;`, and `SettingTab.update()` (`@since 1.13.0`, vs `minAppVersion` 1.7.2 — `no-unsupported-api` would flag it). **Keeping `musicUrl` as slot 1 also means there is no URL migration at all and a rollback to 0.5.6 is lossless.** (For the record: 1.13 _does_ have a real dynamic-list API — `SettingDefinitionList` with `addItem`/`onDelete`/`onReorder` — it was rejected on the minAppVersion/both-paths grounds above, not for lack of capability.) **Positions are keyed per URL, not per slot** (`musicPositions: MusicResumeState[]`, each entry carrying the `url` stamp 0.5.6 introduced): a position belongs to a link and follows it across slots, so **switching stations retires nothing** (A→B→A resumes A — the whole point of a picker), while editing or clearing a slot retires the orphan through ONE sweep driven by the slot list — `reconcileMusicStations()` replaces `retireMusicPositionOnUrlChange()` (it also **heals the selected slot**, writing the resolved index back — without that, the stored index can point at an empty slot while playback runs on the fallback, and filling that slot would silently move playback onto it; the UI key uses the **resolved** slot, not the raw setting, so healing cannot loop), and **delete needs no code path of its own**. That sweep lives in the view's new **`lastStationUiKey`** block, deliberately separate from `lastMusicKey` and running **before** it: the embed key holds only the **active** URL, so it can never see an edit to a slot the user isn't listening to, and names/inactive slots must stay out of it or a rename would reload the player. The UI key is **newline-delimited** (names and URLs are free-form; a printable separator could be typed into one and make two configurations compare equal — and the destructive sweep sits inside that guard). New pure helpers in [youtubeMusic.ts](youtubeMusic.ts), all node-tested, **zero existing signatures changed** so every 0.5.6 test lock stays green: `resolveStationIndex` (the stored index is a preference, never trusted — falls back to the first filled slot, then 0; healed at load so stored ≡ resolved, else pasting into an unused slot could silently redirect playback), `stationLabel` (blank name → slot number, display-only), `findPositionForUrl`, `retainPositionsForUrls`, `normalizeMusicPositions` (defensive load: drops non-objects, unstamped/blank URLs, non-finite or negative seconds, and **duplicate stamps** — two entries for one URL would make lookup order-dependent), `stationsAreSettled` (0.5.6's trap (iv) generalized: the pre-1.13 settings path commits per keystroke, so the sweep refuses to act while ANY slot is mid-edit). **`buildMusicIframe` now takes `sourceUrl` as a parameter** rather than reading `settings.musicUrl` — that field is the provenance stamp every recorded position carries, and the compiler cannot catch a wrong-but-valid string; same reason `notifyMusicError` logs `musicSourceUrl` (after a switch the live setting names a different link). ⏹ Stop captures `stopUrl` **at click time**, not in the fade landing (~450ms later the user may have switched); `destroyMusicIframe` reads the frozen `musicSourceUrl` **before** nulling it, because teardown is invoked FROM the switch's own rebuild, so settings already name the INCOMING station. **Selecting a station never auto-plays** (user decision) — which deleted the two nastiest hazards adversarial review found in the design: a stranded auto-play flag firing on an unrelated later rebuild, and one panel's tap silencing every other open panel. (The ⏭ button added later in 0.5.7 is the ONE exception, and it re-opens exactly those two hazards deliberately — see the ⏭ paragraph below for the four guards that bound them. The picker itself is unchanged: `selectMusicStation`'s default is still "select only".) It also means **no fade on switch** — a fade would have to carry "now actually switch" in a ramp completion callback, and `cancelMusicRamps` drops those, so a duck/▶️/reconcile inside the window would leave the setting changed and the iframe not; teardown is instant, so it cannot desync. `musicSectionVisible` **split from `embedUrl !== null`** to "any slot non-empty" — tying it to the active URL parsing would hide the picker exactly when a bad link needs switching away from. `clearMusicPosition(url)` is now station-scoped and `clearAllMusicPositions()` serves the resume-off toggle (both settings paths still save unconditionally — 0.5.6 finding (iii)). Migration: a pre-0.5.7 single position folds into the list under its own stamp; an unstamped (pre-0.5.6) one is still retired once. **Residual, accepted:** a permanently-unparseable slot (reachable on BOTH paths since the link-check work below moved the URL rows off the `validate` hook, and via hand-edited data.json) keeps `stationsAreSettled` false, so orphans linger in data.json; they can never be _applied_ (planResume's URL gate still refuses them) and the list is capped at `MUSIC_STATION_LIMIT`, but re-pasting that old link would resurrect its position.

**0.5.7 then added five more, all on top of that station machinery.** **(1) The picker is now a caption + expander**, not a segmented row: one quiet `.gp-station-current` line reading `Music | <station>` while idle and `Now playing | <station> | <track>` once audio is actually running (picking a station does not start it, so the idle wording must not claim otherwise; the wording is **read from `setMusicButtonsPlaying`, the single funnel for what the transport shows, not recomputed** — two reasons, both of which bit: `fadeMusicOut` flips the buttons BEFORE setting `musicFadePhase = "out"`, so a recompute there still sees PLAYING and the caption stayed on "Now playing" until the embed confirmed the pause a fade-length later; and `applySettings` is driven by `TimerEngine`'s emit, whose interval early-returns while no session is running — so a per-tick reconcile is simply _not running_ in the case where someone is only playing music, which is exactly when the caption matters most. Driving it from the funnel makes wording and button agree by construction and needs no tick at all), the track half only for a playlist — a playlist moves between items under one unchanged link, so the station name alone stops answering "what is this?", while a plain video is its own track and naming it twice is noise. That title costs no request: the ~4Hz `infoDelivery` stream already carried `videoData.title` and `parsePlayerMessage` was discarding it (one existing test fixture even supplied one), so it is now decoded and gated behind its own render key, or the stream would rewrite the DOM several times a second. Both halves ellipsize, which needs `min-width: 0` on the flex children or no ellipsis ever appears, and the separators are drawn in CSS so they can never land inside a station name or in its DOM text. The `Music`/`Now playing` words are **both present at once** and hand over **in sequence, not as a cross-fade**, with no timer anywhere: the arriving word's transition carries a delay equal to the departing one's duration, so the two never overlap (`--gp-caption-fade` on `.gp-station-current-label` is the single knob; the visible length is twice it). Width rides `max-width` rather than taking the hidden word out of flow — both stay in flow, so the label is always exactly as wide as what it currently says and the separator sits against it, and the change eases instead of snapping, which an absolutely-positioned word cannot do since `position` is not animatable. Two earlier shapes were wrong: stacking both in one grid cell cross-fades but leaves the label permanently as wide as the LONGER word, so "Music" trailed a gap; taking the hidden one out of flow fixes the gap but snaps the width and lets the wider outgoing word overhang the separator. Collapsed controls carry **`inert`**, not just a class: `gp-hidden-animated` and a closed `.gp-task-list` are `max-height: 0`, which does not remove anything from the tab order, and `pointer-events` does not gate Enter on a focused control — so Tab reached invisible buttons that skipped tracks or silenced playback. Hovering shows the whole line as a `title`, but **only while something is actually cut** — measured (`scrollWidth > clientWidth`) rather than assumed, since it turns on the panel's width and not on the text, and re-measured from the ResizeObserver as well as on each render. Writing `title` cannot affect layout, so that read is safe inside the observer callback. The caption is deliberately NOT a control — the list button is the affordance, and a second, heavier one for the same job was the first thing device testing rejected; it is also the only place that name is visible — the per-row tooltip is `title`, which Obsidian suppresses on touch, and `aria-label` was rejected because it REPLACES the accessible name, so a screen reader would read a 60-char URL instead of "Lofi"), plus a list-icon button in the transport row shown at ≥2 links. The list reuses `.gp-task-list` / `.gp-task-item` / `.gp-task-selected` **wholesale** — border, radius, padding, open animation, hover and selected treatment, line spacing, scroll cap and both mobile overrides — departing in exactly two ways (`background-color: transparent`, so the only background colours in the list are the hover and the active row; and a slower 0.55s open, since the task list is something you open to get work done while this is a mood control — the mobile rule that kills the transition outright still wins, being `body.is-mobile .gp-task-list`) and adding only what genuinely differs for a station: a one-line ellipsized label (task text is meant to wrap; a task needs reading, a station needs recognising) and hiding the tick every row carries from birth. **The rows are divs, exactly like `.gp-task-item`, and that is load-bearing:** they were `<button>`s briefly, and Obsidian's own button styling out-specifies a plain class reset, so in dark mode they kept a filled background and the hover never showed at all. Keyboard operability is put back with `tabindex` plus an Enter/Space handler and a `:focus-visible` ring — which the task list itself still lacks. Two pickers in one narrow column that looked merely similar read as a bug. Rows are **built once per slot and only re-labelled** — a rebuild-per-reconcile would leak a detached row and its listener per keystroke, because the pre-1.13 path commits per character, every URL and name is in `lastStationUiKey`, and `Component.registerDomEvent` releases on **unload, not on removal**. Rows stay **positional** (row N ≡ slot N) so an empty middle slot keeps a hidden row rather than shifting the ones after it. A row click **closes the list synchronously before awaiting** the save: `selectMusicStation` fans out through `applySettingsToOpenViews`, which re-enters `applySettings` on the same view, so closing afterwards races a reconcile that has already repainted the row under the handler. The **decorative music glyph was dropped** to make room — `.gp-controls` is a hard 260px column and `.gp-controls-row` is `justify-content: center`, so a too-wide row loses content off **both** ends with no way to scroll back to the start, and the list button (the row's entry point) would have been the casualty; five buttons is 258px, which fits only without the glyph. Icons are hand-built in [icons.ts](icons.ts) beside the day/night set because `addIcon()` wraps its argument in a `0 0 100 100` viewBox, and they carry the `svg-icon` class because the WebKit flex-SVG sliver floor is written against `.gp-icon-btn svg.svg-icon`. **Both custom glyphs use the 24-unit viewBox every Lucide icon uses, and that is load-bearing:** `styles.css` sets `stroke-width` on `.gp-icon-btn svg`, a CSS rule beats a presentation attribute, so a per-icon width set in TS is silently discarded and that one css width resolves against each icon's own user-space — 16-unit art therefore renders 1.5× bolder than its neighbours. ⏭ sidesteps the question entirely by reusing Lucide's `skip-forward`, **the same glyph the timer's own Skip button uses**: both mean "move on to the next one", and two near-identical hand-drawn variants of that idea in one panel read as a mistake. **(2) ⏭ next link carries playback** — `autoPlayOnReady` holds the **target URL, not a boolean**, and is compared against `musicSourceUrl` on the rebuilt frame's `onReady`; it lives on the **view instance, never in settings**, because switching writes a shared setting and every open panel rebuilds, so a persisted flag would start every panel at once. Four guards, each closing a verified hole: it is cleared as the **first statement of `fadeMusicOut`** (not only `destroyMusicIframe` — that method's `!musicPlayerReady` early return lands immediately and destroys nothing, so a ⏸/⏹ during the load gap would otherwise leave the flag standing, drop the command for want of a handshake, and then play: Stop answered with sound); a press **carries an already-pending hand-off** (`|| autoPlayOnReady !== null`) or tapping 1→2→3 ends in silence; it arms **only if a rebuild actually happened** (two slots may hold identical URLs, where `lastMusicKey` never moves and the music never stopped); and `isMusicPlayingForUser` treats a running fade-out as **not** playing, since `setMusicButtonsPlaying` deliberately does not advance `musicPlayerState`. There is still **no fade across the switch** for the reason above; the new station fades in through `startMusicPlayback`, factored out of the ▶️ handler so the two cannot drift. **(3) ⏪/⏩ previous and next video** post `previousVideo`/`nextVideo` (a two-word widening of `PlayerCommandFunc`) from **their own second row**, which keeps row one at four controls — 204px in the hard 260px column, where five was 258px. The row eases in and out on the session controls' curve and durations, collapsing vertically rather than horizontally, and must never carry `gp-hidden`, which is `display:none` and cannot animate. ⏪ is ⏩'s artwork **reflected in CSS**: a reflection is an isometry, so the pair cannot drift in stroke weight the way a redrawn glyph would. Both are shown **only when the PARSED URL carries a `list=`** — never from the message stream, because `buildEmbedUrl` writes `playlist=<own id>` for a looped single video (YouTube's own requirement for `loop=1`) and the embed then reports a one-item playlist, so stream-based detection would put the button on every looped video where it merely restarts the track. **Two things follow from the skip sharing the fade channel, and both were defects first.** `isMusicPlayingForUser` (⏭'s only caller) must read `musicShowingAsPlaying`, **never re-derive from `musicFadePhase`**: an "out" phase now means a pause _or_ a skip, so treating it as stopped made ⏭-inside-a-skip hand over nothing — and the mirror was worse, since a ⏸ landing nulls the phase while `musicPlayerState` is still PLAYING, so for that round trip the old predicate said "playing" with ▶️ already showing and ⏭ answered a pause with sound. And a skip's `clearMusicRampTimers()` kills `duckRestoreTimeout`, the only thing holding an in-flight duck, so the fade-in swelled to full volume under a still-ringing cue (**fade trap 4, through a path that did not exist before skips faded**): `duckHoldUntilMs` is stamped at the **top of `duckMusic`, before every guard** (so a cue arriving mid-skip still records what it is owed), re-offered from the skip's landing, and cleared in `cancelMusicRamps` rather than `clearMusicRampTimers` so it survives a skip but not a teardown. **It rides the same ramp as ▶️/⏸/⏹** — `fadeMusicOut` down, `nextVideo` on the landing, `armMusicFadeIn` straight after — because posting it bare cut one track dead and dropped the next in at full volume, the exact thing this feature family exists to prevent. `fadeMusicOut` therefore takes a `keepShowingPlaying` flag: a skip is not a pause, and flashing ▶️ (and "Music") for a fade-length before flipping back reads as the player stumbling. Three properties fall out of putting the switch in the ramp's completion callback: a ⏸/⏹ landing inside the fade **cancels the advance and wins** (`cancelMusicRamps` drops the callback), `armMusicFadeIn` takes its **still-running** branch because the player was never halted (so it ramps up from `musicRampLevel`, which the fade-out left at 0, and its `holdWhile` spends the rise on audio rather than on the buffering gap), and a **no-op advance** — last item, no loop, bogus `list=` — degrades to a dip-and-swell rather than to silence, because that branch never waits on a transition that will not come. It clears `pendingResumeSeconds`/`resumeSeekLanding` **on the landing, not the click** (a seek posted for the outgoing item blocks `trackMusicPosition` until the new item's clock passes the old offset; clearing on the landing means a cancelled advance leaves the outgoing item's bookkeeping untouched) but **deliberately NOT `musicCurrentDuration`/`musicCurrentVideoId`**: `duration` rides only the fuller state-change payloads, and a no-op advance produces no state change, so a nulled duration would never be restored and `isResumablePosition` reads null as "live stream" — 0.5.4 trap 5 verbatim. **(4+5) One oEmbed probe per pasted link** drives both the inline error and the name prefill. The URL rows became **`render` rows on both paths through one shared builder** (`buildMusicUrlRow`), which means the declarative `validate` hook is gone: it is awaited inside the control's own per-keystroke handler with no debounce and no sequencing, so a slow answer to an old keystroke could land after a newer one — the debounce and the per-slot monotonic token had to live outside it. Consequence: **an unparseable URL now persists on 1.13** instead of being refused (matching pre-1.13), and the mount-time paint of a stored-bad URL had to be restored by hand. The probe is built from the **canonical `MusicTarget`, never the raw string** (oEmbed 404s on `/embed/<id>`, `/v/<id>` and every nocookie watch URL, all of which `parseYouTubeUrl` accepts and the embed plays), asks the **nocookie host** so the whole network surface stays on one already-disclosed domain, and asks about the **playlist** when one is present (a `watch?v=X&list=L` probe answers with X's title, but `planResume` moves the video within the list). Status map, verified live, and **not the intuitive split**: **400 = structurally invalid ID** — YouTube's 11th character encodes only 16 values, so 400 fires for a mistyped _last_ character and little else — while **404 is where an ordinary typo lands**, alongside genuinely deleted videos, so that wording leads with "check the link" rather than blaming deletion. 401 = embedding refused; **`RD*` mixes 404 yet play fine** and so stay silent; **everything else says nothing** — a false "this link is broken" is worse than no check. **No message may claim a link will play**, which is not knowable here (the embed's playability turns on the `Referer` the iframe sends; 0.5.6 documents an oEmbed-clean link that played on macOS and died on iPad), and a test locks the wording against it. The prefill takes the **title**, with the channel as fallback (of this vault's three links one title is a lone ZWJ, i.e. invisible, so the fallback is not theoretical), then `normalizeNameCase`: an all-caps title is sentence-cased and a lowercase opening is capitalised, but a mixed-case first word (`iPhone`) is left alone. Over-long titles are cut at a word boundary when one falls late enough. `visibleNameText` keeps **U+200C/U+200D when they sit between two non-space characters** and drops them everywhere else — they are the one invisible class that changes what its neighbours render as, so a blanket strip turned 👩‍🌾 into two glyphs and misspelt Persian and Indic words; the _emptiness_ test still discounts them, so a name that is nothing but joiners still falls back to the slot number. That last case also hardened `stationLabel`, which only trimmed: `visibleNameText` gates on **"did anything visible survive"** rather than on a strip list, since `\p{Cf}` misses the Hangul fillers, the Braille blank and the Mongolian vowel separator, none of which trim away. Names are also **whitespace-collapsed**, load-bearing because a network-sourced name is the first value that never passes through a single-line input, and `lastStationUiKey`'s newline delimiter was chosen on exactly that assumption — with the destructive orphan sweep inside that guard. Staleness follows 0.5.6's provenance rule: the URL is **frozen at issue time** and compared on landing, a per-slot token drops superseded answers, and `hide()` bumps every token. The prefill is an **offer, never an overwrite** — it needs the stored name empty, the visible box empty, the caret elsewhere, and the box still connected, because a trimmed setting reads empty while the user has their cursor in it. The error element is plugin-owned (`Setting.setErrorMessage`/`errorEl` are 1.13-only and would fail `no-unsupported-api` at `minAppVersion` 1.7.2). **One pre-existing defect was found and fixed in the same branch:** a pending ⏹ suppressed the **incoming** station's resume plan (the flag belongs to the outgoing one, but the plan is computed before `destroyMusicIframe` clears it). **A second "fix" in this branch was a self-inflicted regression, reverted — do not re-apply it.** `destroyMusicIframe` looks as though it never resets `musicPlayerState`, but it does: its closing `updateMusicButtons(YT_STATE.UNSTARTED)` assigns the field before doing the ▶️/⏸ swap. Resetting the field separately _above_ that line puts the call behind its own `state === musicPlayerState` early return, so the swap never runs and every teardown-while-playing leaves ⏸ on screen with **no play button** — killing the release's headline gesture (pick a station, press ▶️), and never recovering within the session when no iframe is built at all. The hazard the reset was meant to close (a stale PLAYING making `armMusicFadeIn` skip the `setVolume(0)` park) was never reachable, for the same reason.

**0.5.6 fixed:** three defects in the remembered-music-position feature, all found by auditing "what if the user edits the URL while the previous one is paused rather than stopped?" **(1) The plugin still emitted `start=`** — not for the resume offset (0.5.3 moved that to a seek precisely because a `start=` embed, alongside the loop feature's `loop=1&playlist=<self>`, stops responding to `playVideo` after a `pauseVideo` and recovers only on `stopVideo`), but for the **user's own pasted `t=`**: `parseYouTubeUrl` → `target.startSeconds` → `buildEmbedUrl` set the param, so anyone pasting YouTube's "copy link at current time" got a player that went permanently silent on ▶️→⏸→▶️. `buildEmbedUrl` now **never** writes `start=` for any offset from any source (test-locked across `90 / 0 / null`), and `planResume` returns the URL's own `t=` as its **fallback** `seekSeconds` — deliberately with **no `MUSIC_RESUME_MIN_SECONDS` floor** (that floor exists to stop a barely-started track being "resumed"; a pasted `t=3` is an explicit instruction). Now that a pasted offset actually reaches playback, `parseYouTubeUrl` also reads the **legacy `#t=` fragment** form (`youtu.be/<id>#t=1m30s`) — such links parsed fine before but their timestamp was silently dropped. The hash is parsed as a query string (so `#t=90&…` works) and consulted **last**: an explicit `start=`/`t=` param is the modern share format and wins, and a fragment carrying no `t=` yields null rather than throwing. **(2) A stored position outlived the URL it came from.** It was keyed by video + playlist context only, so two deliberate edits were silently overridden — a switch to a different item of the **same playlist** (planResume's "inside a list the saved video wins" rule, correct for reopening an unchanged URL, hijacked the pasted item) and a changed `t=` on the same video (the stored offset beat it) — both **sticky**, since every later rebuild re-planned from the same store, and unrecoverable without ⏹ _plus_ closing the panel. Fix: `MusicResumeState` gains a `url` stamp = the `musicUrl` **setting string** it was recorded under, and new pure `musicPositionAppliesToUrl(savedUrl, currentUrl)` (trim-tolerant — data.json is hand-editable) gates `planResume`, which now takes `currentUrl` as a third argument. Per user decision the position is also **erased**, not merely ignored: `GentlePomoPlugin.retireMusicPositionOnUrlChange()` runs in the view's musicKey block — after `parseYouTubeUrl`, before the plan is worked out, so the edit is honoured on the very rebuild it triggers — and covers an edit from either settings path, another view, or a synced data.json. It is **gated on the URL being parseable (or the field emptied), and deliberately NOT on `target`**, which is also null whenever the player is merely hidden: keying the erase off visibility meant a URL edit made with the player off kept its old position, so hiding the player silently changed what an edit meant. See (iv). **Both layers are load-bearing, not duplication:** the erase can't run while no view is open, so the `planResume` gate is what holds the invariant then. `recordMusicPosition` takes a full `MusicResumeState` and stamps **`position.url`, never `this.settings.musicUrl`** — provenance travels with the position, from the view field (`musicSourceUrl`) frozen when that iframe was built; see (i) below for the race that reading the live setting caused. The stamp is **part of its dedupe early-return**, or a stale stamp would never be rewritten. **(3) A trap the fix itself created:** with no offset left in the embed URL, editing _only_ the `t=` produces a **byte-identical** embed URL, so the `embedUrl !== lastMusicEmbedUrl` rebuild guard skipped the rebuild and the freshly-computed seek was dropped on the floor — finding 2 reappearing through the fix for finding 1. The guard therefore gained a second key — **`lastMusicSourceUrl`**, the `musicUrl` setting the live build came from (null when nothing is embedded, so a player-less view doesn't rebuild on its first tick); it can only fire on a real edit, since the whole block is already behind `lastMusicKey`. (The first cut keyed on the seek itself, which (ii) below shows was still the same bug one step removed.) Also: the pending seek is now **consumed but not posted** when `musicCurrentDuration <= 0` (how the embed reports a live stream — an offset means nothing there and `start=` was ignored outright, whereas a raw `seekTo` would land far outside the DVR window); only skipped when _positively_ known live, since duration is null until the info stream carries one. Stored positions are never live (`isResumablePosition` refuses them) — only a pasted `t=` can be. Settings schema gains `lastMusicUrl` (internal state, `null` default, normal `Object.assign` merge); a pre-0.5.6 position has no stamp and is **retired once** on the first plan after upgrade — its provenance is unknown, and guessing the current URL would guess wrong in exactly the case the stamp was added for. `MUSIC_RESUME_DESC` and the README bullet gained the "or change the URL" clause. **Also in 0.5.6, prompted by a report that some links play on macOS but not on iPad — two ways the plugin could be talking to a player that isn't listening. Both fail silently, both are video- or device-dependent, and neither is iOS-specific in principle:** **(a) outbound commands were pinned to the origin we loaded.** `postToMusicPlayer` hardcoded `YT_EMBED_ORIGIN`, yet `YT_ALLOWED_MESSAGE_ORIGINS` has always admitted `www.youtube.com` **inbound** precisely because the player bounces there for some videos — and `postMessage` delivers nothing when `targetOrigin` doesn't match the frame's _current_ origin. After a bounce every `playVideo`/`pauseVideo`/`setVolume`/`seekTo` was dropped by the browser: no error, no state change, `musicPlayerReady` still true, ▶️ apparently working. New `musicPlayerOrigin` field tracks the origin the embed last messaged us from (already allowlist-checked on the way in), reset to `YT_EMBED_ORIGIN` in `destroyMusicIframe` since a learned origin belongs to the frame that taught it. **(b) The `listening` handshake was fire-and-forget** — one post, `MUSIC_LISTENING_DELAY_MS` (100ms) after the iframe's `load`. Miss that window (slower device, cold cache, heavy stream) and the embed never installs its listener, never streams an event, and the panel answers ▶️ with "the player hasn't loaded" for as long as it stays open. `beginMusicHandshake` now re-posts every `MUSIC_HANDSHAKE_RETRY_MS` (600ms) up to `MUSIC_HANDSHAKE_MAX_ATTEMPTS` (8), stopped by `stopMusicHandshakeRetries` on the **first message of any kind** from the frame — even one `parsePlayerMessage` discards, since it still proves the embed heard us — and in `destroyMusicIframe`; a healthy player pays exactly one timer that never fires. The handshake is **broadcast to every allowed origin**, because it goes out before there is any learned origin to aim at; only the frame's real origin receives it, so the embed can never be handed a duplicate. **Neither is confirmed as the cause of the iPad reports** (no device here to reproduce on) — they are real defects on their own terms. The documented iOS first-play limit (autoplay needs an in-iframe tap and the player is hidden, so none exists) is untouched and remains a platform constraint, as does `.gp-music-player` staying **rendered** (1×1, `opacity: 0`) rather than `display: none`. **(c) The error Notice couldn't be triaged.** One generic sentence covered codes 2, 5 and 100 — and since the player is hidden there is no YouTube error screen behind it, so that Notice is all a user ever sees. The reporter's link (a normal, oEmbed-embeddable Lofi Girl video that plays on macOS) produced exactly that message on iPad, which narrowed it to those three codes and no further. **0.5.4 added:** the music **fades in and out** on ▶️/⏸/⏹ instead of snapping (user request: make the audio change sound smoother). Shape: ▶️ parks the embed at `setVolume(0)`, posts `playVideo`, and **arms** the fade — the ramp only runs on the first PLAYING transition, because `playVideo` is followed by a buffering gap with no audio in it and a fade spent on silence is a fade nobody hears; ⏸/⏹ ramp **down to silence first and post `pauseVideo`/`stopVideo` on the landing** (posting it up front cuts the audio dead and leaves the fade nothing to fade). New pure `buildFadeRamp` in [youtubeMusic.ts](youtubeMusic.ts) beside `buildVolumeRamp`: identical contract (excludes `from`, lands exactly on `to`) but **quadratically weighted toward the quiet end** — loudness is perceived roughly logarithmically, so a linear amplitude ramp spends half its time inside the top 6 dB and sounds like the music snaps in and then hangs; the eased ramp sits a quarter of the way up from the quiet end at the halfway point, and a fade-out is the exact mirror of the fade-in that undoes it. **Ducking keeps the linear `buildVolumeRamp`** — it moves between two audible levels, where the curve would only make the dip feel late. Constants ([constants.ts](constants.ts)): `MUSIC_FADE_IN_MS` 800 / `MUSIC_FADE_OUT_MS` 450 (asymmetric for the duck's own reason — the out-fade _delays the pause_, so it must stay short enough that the button feels immediate) / `MUSIC_FADE_STEP_MS` 50 / `MUSIC_FADE_ARM_TIMEOUT_MS` 5000 / `MUSIC_FADE_HOLD_MAX_MS` 3000.

**Ducking and fading share ONE ramp channel**, so they can never post over each other: `duckRampInterval`/`duckLevel`/`runDuckRamp`/`cancelMusicDuck` became `musicRampInterval`/`musicRampLevel`/`runMusicRamp`/`cancelMusicRamps`, and `runMusicRamp(levels, stepMs, onDone?, holdWhile?)` takes a **prebuilt level array plus an explicit `stepMs`** — the first cut defaulted `stepMs` and silently ran the duck's down-ramp at the fade's 50ms cadence, shortening a 240ms dip to 200ms, so the step count and the cadence must always travel together. `musicFadePhase` (`"armed" | "in" | "out" | null`) is the fade's state; a pending `pauseVideo`/`stopVideo` lives in the ramp's completion callback, so **replacing or clearing the ramp is what cancels the command**.

**Seven traps this feature is built around** (all found by adversarial review before shipping; re-introducing any of them is a silent-music or lost-position bug):

1. **⏸ → ▶️ inside the fade-out must not arm.** Cancelling the ramp drops the pending `pauseVideo`, so the player _never stopped_: `playVideo` is a no-op, no `onStateChange` follows, and the ~4Hz `infoDelivery` repeats are filtered out by `handleMusicState`'s `state !== musicPlayerState` guard. An armed fade would wait forever with the volume parked at 0 — and since `postMusicVolume` early-returns while a fade is in flight, the volume control would go dead with it. `armMusicFadeIn` reads `musicPlayerState` **before** clearing and, when the player is still running (PLAYING _or_ BUFFERING — a rebuffer mid-fade-out is the same trap), eases straight back up from the abandoned level instead of arming.
2. **A dropped `playVideo` must not strand the arm** (iOS refusing a first play, a dead video): `MUSIC_FADE_ARM_TIMEOUT_MS` stands the fade down and re-posts the user's volume — inaudible, since nothing is playing, and it hands the volume control back. If the player is merely **buffering slowly** when the backstop fires it hands over to `beginMusicFadeIn` instead of cancelling, because the ramp holds itself until audio starts (trap 3) — cancelling there would make a slow connection snap in at full volume, which is the one thing this feature exists to stop. `postMusicVolume`'s skip path deliberately **does not stamp** `lastAppliedMusicVolume`, so `applySettings`' convergence check keeps retrying and heals the moment any fade ends.
3. **The 0.5.3 resume seek rebuffers**, and the fade-in starts on the very PLAYING transition that posts the `seekTo`. `runMusicRamp`'s `holdWhile` predicate (fade-in only) skips ticks while the player isn't PLAYING, so the ramp waits the rebuffer out instead of running through the silence and arriving at full volume. Bounded by `MUSIC_FADE_HOLD_MAX_MS` so a player that never returns can't strand it half-way up.
4. **A cue during a fade-in must still duck.** "Press ▶️, then press Start" puts the war drum squarely in the fade window, and blocking the duck there would leave a cue playing over music rising to full volume — precisely what ducking exists to prevent. `duckMusic` therefore **takes the volume over** during `"armed"`/`"in"` (clearing `musicFadePhase`, because the abandoned fade's landing callback dies with the replaced ramp) and its restore ramp finishes the rise. A fade-**out** still wins: the player is about to pause, so there is nothing to duck.
5. **⏹ Stop has to stay atomic.** Its `stopVideo` now rides in the ramp's landing callback, which a ▶️ press cancels — so **every** part of Stop moved into that callback with it (`clearMusicPosition`, `pendingResumeSeconds`, `resumeSeekLanding`, `musicCurrentDuration`). The first cut cleared them on the click, and an aborted Stop then left `musicCurrentDuration` null forever, which `isResumablePosition` reads as "live stream" — position recording silently dead for the rest of the track. Only `musicStopPending` is set on the click (it blocks `trackMusicPosition` while the fade still plays audio, so those last seconds can't re-bank the position Stop is about to drop). **The flag's lifecycle is exactly the straggler window**: `armMusicFadeIn` clears it (aborted Stop), and a _landed_ stop is **settled** — flag down — on the first non-audible transition afterwards (or at the landing itself when the player was already halted, since no further transition may come). Leaving it up past that point was itself a lost-position bug: trap 7's resume path never passes through ▶️, so a stuck flag killed recording for the whole resumed session. While the flag is up, `applySettings`' rebuild path **plans resume against an empty store** (a Loop flip inside the 450ms window would otherwise snapshot the position the stop is mid-way through forgetting and seed the new iframe with it), and `destroyMusicIframe` **honours the pending stop** — `clearMusicPosition()` instead of `flushMusicPosition()`. (`resumeSeekLanding` was already leaking in 0.5.3's Stop handler; this is where it got fixed.)
6. **A volume change during a fade-in must win immediately** (0.5.0's promise). The ramp snapshots its target at build time, so `postMusicVolume` **re-aims** a `"in"` fade by rebuilding it from the current level — and, uniquely on that path, **does** stamp `lastAppliedMusicVolume`: leaving it stale there would have `applySettings`' ~20Hz check rebuild the ramp every tick, restarting it faster than a single step could fire. The no-stamp rule in trap 2 applies only to the phases that don't act on the value — and `duckMusic` **stamps the setting when it takes a fade over** (trap 4), because inheriting a stale stamp there would have the next 50ms tick cancel the duck it just started.
7. **A landed ⏸/⏹ parks the embed at volume 0, and playback can resume without ▶️.** Hardware media keys drive a YouTube embed in Electron; in 0.5.3 pause kept the user volume so a media-key resume was audible — silent playback with ⏸ showing would be the regression. `handleMusicState` detects the orphaned park (transition into an audible state **from a halted one**, no fade phase, no ramp timers, `musicRampLevel` still non-null) and fades up from the parked level — re-arming instead when the edge is BUFFERING, so the fade isn't spent on silence. The **from-a-halted-state** condition is load-bearing: a straggler PLAYING that races the just-posted `pauseVideo`/`stopVideo` arrives from a still-audible previous state and must not trigger it. Related: the `"armed"` stand-down fires **only on PAUSED/ENDED** — the embed emits transient UNSTARTED/CUED on its way to playing, and treating those as dead ends cancelled the fade and let the music snap in (the arm timeout covers a player that truly never starts).

Also: `maybeNotifyMusicEnded` is suppressed while `musicFadePhase === "out"`, since a track ending inside the fade would answer the button press with "the music ended — paste a new link"; `setMusicButtonsPlaying` is split out of `updateMusicButtons` so a fade-out can swap the ▶️/⏸ buttons **immediately** (waiting a fade-length for YouTube to confirm leaves the button looking dead) **without** touching `musicPlayerState`, which the flush / resume-seek / notice logic still reads as the real previous state — and `updateMusicButtons` lets an in-flight fade-out win, so a rebuffer or playlist advance can't put ⏸ back moments after it was pressed. `fadeMusicOut` skips the ramp entirely unless the player is actually running, so ⏹ on an idle player still forgets instantly. No settings, no schema change, no new network surface; `buildFadeRamp` is node-tested in [tests/youtubeMusic.test.ts](tests/youtubeMusic.test.ts).

**0.5.3 added:** the lofi player **remembers where it was** and reopens there (user decision: **restore the position, never auto-play** — Obsidian startup must not burst into music, and iOS blocks first-play without an in-iframe tap, which the hidden player has none of). Capture: `parsePlayerMessage` in [youtubeMusic.ts](youtubeMusic.ts) no longer throws away everything but `playerState` — `infoDelivery` now decodes to a new `{type:"info", state, currentTime, duration, videoId}` variant (every field nullable; the stream sends them piecemeal, never all at once), which is the ONLY way to read the clock (the postMessage protocol has no request/response getters — the JS API's getters just read a cache fed by this same stream). Storage: internal state fields `lastMusicVideoId`/`lastMusicPlaylistId`/`lastMusicSeconds` in [types.ts](types.ts) beside `lastGoalHitDate`, plus the user-facing `musicResume` toggle (default `true`, Music group in **both** settings-tab paths, desc shared via `MUSIC_RESUME_DESC`). The plugin owns persistence (`recordMusicPosition` / `clearMusicPosition` / `flushMusicPosition` / `musicResumeState` in [main.ts](main.ts)); the view owns the running picture. **Write amplification was the design constraint** — data.json lives in the vault, so every save is sync traffic: the ~4Hz stream only mutates in-memory fields (deduped to whole seconds, so ~1 update/sec, no disk), and the _save_ happens on boundaries — PAUSED, ⏹ Stop, ENDED, `destroyMusicIframe` (panel close / leaf move / URL change), `onunload` — with a dirty-flag-gated `MUSIC_POSITION_SAVE_MS` (60s, [constants.ts](constants.ts)) `registerInterval` as the force-quit backstop (worst case ≤60s of drift; a quiet beat is one boolean check).

**Restore does NOT touch the embed URL — this is the load-bearing part.** The first cut of 0.5.3 folded the offset in as `start=`, and it broke playback (user-reported): an embed loaded with `start=` — alongside the loop feature's `loop=1&playlist=<self>` — **stops responding to `playVideo` after a `pauseVideo`**, recovering only on `stopVideo`. (Ruled out plugin-side: nothing gates `playVideo` but `musicPlayerReady`, which only `destroyMusicIframe` clears, and pause never calls it. Also not a resumed-past-the-end case — the reporter's video was 2h22m and the offset 129s.) So pure `planResume(target, saved)` returns a `{target, seekSeconds}` plan whose target is **byte-identical to what 0.5.2 built** (returned by _reference_ when the video is unchanged), and the offset rides as a one-shot `seekTo` posted from `handleMusicState` on the first PLAYING/BUFFERING transition — the only state YouTube documents as safe to seek from (from a _cued_ player `seekTo` starts playback, i.e. exactly the auto-play this feature must not do). Consuming it on BUFFERING usually lands the jump before any audio. Everything about playback, looping, ⏹ Stop and close-the-panel-to-stop therefore behaves exactly as in 0.5.2, and the earlier `musicSeekToZeroOnPlay` hack (which existed only to undo a `start=` that YouTube re-applies on every loop repeat) is gone. The plan is read **at iframe-build time only, deliberately NOT part of `lastMusicKey`** — keying on a value that moves every second would rebuild the iframe ~20×/sec (the iPhone-flicker regression family). A posted seek sets `resumeSeekLanding`, and `trackMusicPosition` ignores clock readings below it until it lands, so the pre-seek `currentTime: ~0` can't overwrite the position being resumed to (if the seek is never honoured nothing is recorded, leaving the stored position intact for next time).

**Resume is keyed by video ID, not playlist index** (`index=` is 1-based while `infoDelivery.playlistIndex` is 0-based, and an index breaks when the playlist is reordered): a playlist _item_ still has to come from the URL, since a seek can't cross items, so `planResume` swaps `target.videoId` for the saved one — `/embed/<id>?list=<list>`, the shape a watch+list URL already produced in 0.5.0. The list context must match exactly, so a changed URL never inherits an offset. Guards, split by side: `isResumablePosition` (record side) drops the last `MUSIC_RESUME_END_MARGIN_SECONDS` (10s) of a track and anything with a non-positive `duration` — **which is how a live stream reports, so streams never store an offset**; `planResume` (apply side) drops anything under `MUSIC_RESUME_MIN_SECONDS` (5s). The floor lives on the apply side _on purpose_: recording the opening seconds is what lets a restarted/looped track immediately overwrite a stale offset. **⏹ Stop = forget** (user's own framing — pause remembers, stop forgets; it doubles as the manual "start from the top" control with no new UI), dropping both the stored position and any pending seek; ENDED clears too. New pure helpers are node-tested in [tests/youtubeMusic.test.ts](tests/youtubeMusic.test.ts), including a regression test asserting the built URL contains no `start=`. No migration (the `Object.assign` merge covers the new fields), no new network surface, no README **Network use** change.

Three task-picker `.onclick` handlers converted to `registerDomEvent`. **Control-glyph sizing**: a `min-width`/`min-height` floor on `.gp-icon-btn svg.svg-icon` in the Mobile & touch CSS section — a workaround for a WebKit/Safari flexbox bug that collapses an SVG flex item's main-axis width to ~8px on iPad (see Important Quirks). **Daily-log robustness**: `writeLog` now resolves the file via the Vault index with an adapter-append fallback (no silent drops under mobile/sync index lag), wraps the write in try/catch + `Notice`, and tolerates a folder-create race; log-folder scans use boundary-safe `isPathInFolder` (from [taskLoader.ts](taskLoader.ts)) instead of `path.startsWith`. ## Architecture

State flows through a listener pattern:

```
GentlePomoPlugin (main.ts)
    │
    ├── TimerEngine ──emit(TimerState)──▶ GentlePomoView   (renders the visual timer)
    │                                  └▶ status bar in main.ts
    │
    ├── LogManager       (appends daily-log markdown lines, TTL cache for today's totals)
    └── GentlePomoSettingTab  (Obsidian PluginSettingTab)
```

- `TimerEngine` is the single source of truth for timer state. Every subscriber gets a fresh snapshot via `onChange`.
- The view does **not** own state — it reads from `TimerEngine` and dispatches user actions back to it.
- Persistence is Obsidian's `loadData()`/`saveData()`; defaults are merged from `DEFAULT_SETTINGS` in [constants.ts](constants.ts).

## Conventions

- **State updates flow through `TimerEngine.emit()`** → listeners. Never mutate `TimerState` from the View or status bar.
- **Defaults live in [constants.ts](constants.ts)** `DEFAULT_SETTINGS`. New settings must be added there and merged via `Object.assign` in `loadSettings()` ([main.ts](main.ts) `loadSettings`).
- **Task IDs** are detected via the `🆔` emoji marker. Log entries use Obsidian wiki-link syntax: `[[path|display name]]`.
- **CSS classes are `gp-*` prefixed.** Stay consistent — search [styles.css](styles.css) before inventing new names.
- **Logging:** use `logger.warn/error/debug` from [logger.ts](logger.ts), not raw `console.*`. The prefix `[GentlePomo]` is added automatically.
- **Audio assets** (`ding-sound.mp3`, `singing_bell_short.mp3`, `war-drum_short.mp3`) live at the project root and are loaded by relative path from [TimerEngine.ts](TimerEngine.ts).
- **Task parsing** must go through [taskLoader.ts](taskLoader.ts) (`loadTasks`, `groupTasksByDate`, `normalizeTaskText`, etc.) — never re-implement regex inline.

## Settings & Persistence

`GentlePomoSettings` in [types.ts](types.ts) is the schema. Stored by Obsidian in `data.json` at the project root. Modify via `plugin.settings.foo = ...` then `await plugin.saveSettings()`.

## Log Format

Daily file: `<folder>/YYYY-MM-DD-gentle-pomodoro-log.md`. One line per session, inline-field format so Dataview can query it:

```markdown
- 🍅 Focus | Task:: [[Projects/MyProject.md|Write Docs]] | ID:: abcd12 | Start:: 2025-12-23 10:00:00 | End:: 2025-12-23 10:25:00 | Scheduled:: 1500 | Pauses:: [] | Total:: 1500 | Status:: finished | Type:: focus
- ☕ Rest | Start:: 2025-12-23 10:25:00 | End:: 2025-12-23 10:30:00 | Scheduled:: 300 | Total:: 300 | Type:: short-break
- ☕ Rest | Start:: 2025-12-23 11:00:00 | End:: 2025-12-23 11:15:00 | Scheduled:: 900 | Total:: 900 | Type:: long-break
```

`Type::` was added in 0.1.0 — values are `focus | short-break | long-break`. Additive; existing Dataview queries still match.

Field order is **load-bearing** for users' Dataview queries — do not reorder or rename without a version bump and changelog note. The schema is locked in by [tests/logManager.test.ts](tests/logManager.test.ts).

## Important Quirks

- **`obsidian` dep is pinned to `^1.13.1`** (types-only npm package; 1.13 typings are required for the declarative settings API — `getSettingDefinitions()` in [GentlePomoSettingTab.ts](GentlePomoSettingTab.ts), with the imperative `display()` kept as the pre-1.13 fallback; keep both paths in sync when changing settings). [package.json](package.json) and [manifest.json](manifest.json) track 0.5.7; `minAppVersion` is **1.7.2** (raised from 1.0.0 for `Workspace.revealLeaf` / `Vault.createFolder`, which `eslint-plugin-obsidianmd`'s `no-unsupported-api` rule gates). [versions.json](versions.json) maps each plugin version to its `minAppVersion`.
- **Audio lifecycle:** [TimerEngine.ts](TimerEngine.ts) owns a single shared `AudioContext`, created lazily in `playSound()` and resumed if suspended; decoded clips are cached in `audioBuffers`. `TimerEngine.dispose()` (called from [main.ts](main.ts) `onunload`) closes the context and clears the tick loop — Chromium caps live `AudioContext`s, so it must not leak across disable/enable cycles.
- **The music embed never requests a YouTube playback quality — audited (pre-0.5.7), correct as-is, don't "fix" it.** Nothing in [youtubeMusic.ts](youtubeMusic.ts) sets one (`PlayerCommandFunc` has no `setPlaybackQuality`; `buildEmbedUrl` writes no quality param), and nothing could: the IFrame API's quality setters (`setPlaybackQuality`, the queueing functions' `suggestedQuality` arg) are documented no-ops — the player picks automatically from size + bandwidth, so the 1×1 `.gp-music-player` gets the lowest video rendition. That is the optimum for an audio-only player: audio rides a separate adaptive stream whose quality (~128–160 kbps) is identical at 144p and 1080p, so the one lever that still exists — letting the hidden iframe report a large size — would stream and decode invisible pixels for zero audible gain. The sole case where the video tier touches audio is muxed live-HLS variants (~48 kbps audio at the bottom tiers), which is native-HLS playback, i.e. iOS — where the feature cannot play at all (error 153); desktop Electron plays via MSE with a separate audio track. `parsePlayerMessage` deliberately discards quality-only `infoDelivery` payloads (they are in the stream if a runtime check is ever wanted).
- **`main.js` is the built artifact.** It's gitignored, but Obsidian loads it directly — you must `npm run build` (or have `npm run dev` running) before reloading the plugin.
- **iPad icon sizing needs a CSS `min-width` floor.** WebKit/Safari collapses an SVG flex item's main-axis (width) to ~min-content (~8px) while honoring height, so the control glyphs render as thin slivers — and a plain CSS `width` (even `!important`) does **not** fix it. The fix is a `min-width`/`min-height` floor (+ `flex-shrink: 0`) on `body.is-mobile/.is-tablet .gp-icon-btn svg.svg-icon` in [styles.css](styles.css); the `min-*` floor is the load-bearing part (the flex algorithm can't shrink below it), so don't drop it. It **must** be CSS, not inline `el.style.setProperty` — `eslint-plugin-obsidianmd`'s `no-static-styles-assignment` forbids inline style assignment (and disabling that rule). (Diagnosed device-side via Safari Web Inspector; desktop/iPhone were never affected.)
- **Auto-open** runs inside `this.app.workspace.onLayoutReady()`. A `MutationObserver` fallback waits for any settings/community-plugin modal to close before activating the view (handles freshly-installed-plugin UX).
- **`noImplicitOverride: true`** is enabled in [tsconfig.json](tsconfig.json). Always mark methods that override Obsidian base classes (`Plugin.onload`, `ItemView.onClose`, etc.) with `override`.
- **`package-lock.json` is tracked** — CI uses `npm ci` for reproducible builds (since 0.1.1). Regenerate with `npm install` whenever `package.json` changes.
- **Local-timezone date string** used for daily reset logic is `moment().format("YYYY-MM-DD")` (defined as `todayLocalStr()` in both [main.ts](main.ts) and [TimerEngine.ts](TimerEngine.ts)). Same format as the daily log file naming, so all "today" logic agrees.
- **Per-task counter is opt-in** (`incrementPomodoroCountOnFinish`, default off). When enabled, finishing a focus session linked to a task increments a lifetime `🍅 N` marker on the task line. The marker sits at the **end of the description, before the Tasks emoji fields** (since 0.5.1 — a trailing marker breaks Tasks date parsing, see issue #2) and before any trailing `^block-id`. Legacy `🍅 N (YYYY-MM-DD)` markers from an earlier 0.1.0 build are still readable; on the next increment the parens are stripped, the marker becomes `🍅 N+1`, and a misplaced (≤0.5.0 trailing) marker is relocated in front of the fields.
- **Internal state fields** in `GentlePomoSettings` (`lastGoalHitDate`, `sessionsSinceLongBreak`, `sessionCounterDate`) are persisted to `data.json` alongside user settings but are not surfaced in any settings UI — they implement the once-per-day notice and long-break counter.
- **The music subsystem is ~47% of [GentlePomoView.ts](GentlePomoView.ts) and has NO orchestration tests.** Measured pre-0.5.7: a **contiguous** 657-line block of 24 music-only methods (`buildMusicIframe` → `notifyMusicError`), whose only outward dependencies are `this.plugin` and one `registerDomEvent`, and which touches zero non-music view state — an unusually clean extraction seam. The pure helpers in [youtubeMusic.ts](youtubeMusic.ts) have 13 test suites; the state machine where **every** past music bug actually lived has none, and `__mocks__/obsidian.ts` stubs `ItemView` as an empty class so the view cannot be instantiated in a test. Note the traps are **sequencing** traps ("read `musicPlayerState` _before_ `clearMusicRampTimers()`"; "post `stopVideo` on the ramp's landing, not up front"), so extracting pure predicates would NOT capture them — only a class with **injected I/O** (post-message sink, fake clock) makes them testable. If that extraction is ever done: pure move, no cleanups (the compiler catches renames, not reordered statements), landed alone and never bundled with a feature, and note the _fields_ are slightly interleaved (`lastTimeText`/`lastEndText` are not music) even though the methods are not.

## Don't Do This

- Don't add `setInterval` calls in the view — subscribe to `TimerEngine.onChange` instead.
- Don't touch the DOM from `TimerEngine` or `LogManager` — UI rendering belongs in the View.
- Don't reach into `this.app.metadataCache` for task parsing — use [taskLoader.ts](taskLoader.ts).
- Don't use `console.*` directly — go through [logger.ts](logger.ts) (and `console.log` is lint-blocked anyway).
- Don't reorder or rename inline fields in log lines — tests in [tests/logManager.test.ts](tests/logManager.test.ts) will fail, and users have Dataview queries pinned to the current schema.

## Reusable Patterns

- **Listener pattern:** `onChange/offChange/emit` in [TimerEngine.ts](TimerEngine.ts) — copy this shape for any new subscribable state.
- **Settings merge:** `Object.assign({}, DEFAULT_SETTINGS, loaded ?? {})` in [main.ts](main.ts) `loadSettings`.
- **TTL cache:** `FOCUS_TOTAL_CACHE_TTL_MS` + `lastFetchMs` + `fetchInFlight` pattern in [main.ts](main.ts) `maybeRefreshFocusTotal` and [logManager.ts](logManager.ts) `getTodayFocusSeconds` — reuse for any expensive periodic fetch.
