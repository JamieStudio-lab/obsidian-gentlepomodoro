## Project Summary

**Gentle Pomodoro** is an Obsidian plugin: a soothing, task-integrated Pomodoro timer that links sessions to Tasks-plugin markdown items and writes Dataview-compatible daily logs. Currently **v0.6.4 (beta)**.

**0.6.4 answers [GitHub issue #4](https://github.com/JamieStudio-lab/obsidian-gentlepomodoro/issues/4) — "pick up tasks from the currently opened note" — with a three-way scope on both surfaces.** New [taskScope.ts](taskScope.ts) owns the whole idea: the `TaskSource` union (`folder` / `current-note` / `open-notes`), the shared labels, `resolveTaskScope`, `taskScopeKey`, `taskScopeSummary` and `taskPickerEmptyState`. It is pure — the workspace arrives as a **structural `ScopeWorkspace`**, never Obsidian's `Workspace` — which is what makes the one genuinely dangerous part testable. **That part is `openMarkdownPaths`, and it reads `leaf.getViewState()`, never `leaf.view`:** a background tab has been **deferred** since 1.7.2, so its `view` is a placeholder `DeferredView` that has loaded no file and `getLeavesOfType("markdown")` does not return it at all — "Open notes" would silently have meant "the one tab I am looking at" on any machine with more than a couple open, and it would have looked correct on the dev machine. `current-note` uses **`getActiveFile()`, not the active leaf**, because clicking the timer panel makes the panel the active leaf and the picker must not empty itself the moment the user reaches for it. **The date rule is now per-scope, and that was the user's decision after being shown the alternatives:** the two note scopes pass `includeUndated`, so a plain `- [ ] something` with no ⏳/📅 appears under a trailing **"No date"** group; the folder scope does not, so a wide scan stays readable and **every upgrading user's picker is byte-identical** — `taskSource` defaults to `"folder"` in `DEFAULT_SETTINGS` for exactly that reason (it is the `Object.assign` merge base). `TaskItem.effectiveDateStr` therefore widened to `string | null`, and **every reader must branch on null BEFORE building a moment**: `moment(undefined)` is _now_, so one careless read files every undated task under "Today". `loadTasks` sorts undated last **as a block**, which is the only reason `groupTasksByDate` needs no special case for the trailing group. **Sticky selection is a `pin`, not a persisted flag:** `loadTasks` takes `{path, cleanText}`, reads that note even when out of scope, takes **only the pinned line** from it (or choosing "Current note" would drag in every other task from wherever the linked one lives), bypasses the window and the undated rule for it, and marks it `pinned` only when the scope would NOT otherwise have shown it — so it is lifted into its own **"Linked task"** group rather than listed twice. **The `pinned` predicate was wrong on the first cut and a test caught it**: it read only the date filter, so a linked task in an out-of-scope note went unflagged whenever it happened to fall inside the lookahead window, which is most of them; it now reads `!pinOnly && (date || includeUndated)`. A completed line is never resurrected — `TASK_LINE_REGEX`'s status gate still runs first — which is the maintainer's "unless it is marked as finished". **Nothing unlinks on a scope change**, and a settings-tab test asserts it against the neighbouring `showTaskSelector`, which deliberately does. **UI:** a `dropdown` row in the tab's Task selector group, placed **above** "Tasks folder path" (the choice is what makes that field irrelevant, so it comes first) with the path row **still visible in every source** — 0.6.3 deleted the visibility machinery and nothing here brings it back. The panel gets the plugin's first `selectRow`: a **stacked** `<label>` wrapping its own `<select>` (no id to mint), because a question plus three multi-word options do not share a line in the hard 260px column, plus a `.gp-settings-hint` from `taskScopeSummary` — the same "say what will happen" mechanism 0.6.3's end-of-session lines use, and it re-seeds **with** its control so the sentence can never contradict the choice above it. `taskSource` is the **sixth dual-surface setting**. **Two live triggers keep an OPEN picker honest, split by cost:** `applySettings` compares a three-field `taskSettingsKey()` (source|days|path) on every 50ms tick — resolving the scope there would walk every workspace leaf twenty times a second, the iPhone-flicker shape — while a change of _note_ comes from a single `active-leaf-change` listener that compares `taskScopeKey`, which is **newline-delimited** because its members are file paths and every other printable character is legal in one. `loadTasks` also gained a **monotonic generation token**: switching notes with the picker open genuinely starts a second load, and without it the slower vault read paints over the newer one. **Two pre-existing defects were found while placing this and fixed here.** (1) The panel's registry re-arm block sat **below** the two Timing `numberRow` calls, so `numberPanelRows` was cleared the instant after they registered and the caret-guarded re-seed those rows exist for **never ran once** in 0.6.3 — the same convergence bug for the fourth time. The block moved to the top of `renderSettingsPanel`, and the test now checks **each registry against its own first row** instead of one shared `sharedToggle(` landmark, which is precisely what let this one through; a mutation run confirms the old arrangement now fails. (2) Task rows registered a **click listener per row** while the comment directly above them explained why they must not — `registerDomEvent` releases on unload, not removal — so every picker-open leaked N listeners against detached nodes; one delegated handler now, addressed through `data-gp-task-index`, matching the keydown beside it. The shared-label drift guard for these labels searches **code only** (full-line comments and block comments stripped): they are dropdown option _values_ with no argument shape to match, and a bare substring search fails on the next person who explains the const in a comment — which is what it did on its first run. `loadTasks` and `groupTasksByDate` had **zero tests** before this release; 15 baseline locks landed first, and they use the **real moment 2.29.4** (already in the tree as a dependency of the `obsidian` typings, now declared explicitly) rather than a stub faithful enough to be just moment with more places to be wrong. 580 → 651 tests.

**0.6.3 answers [GitHub issue #5](https://github.com/JamieStudio-lab/obsidian-gentlepomodoro/issues/5) — "no sound when the rest timer is over" — without conceding that it was a bug.** It is not: the silent zero crossing is a **deliberate flow protection** (see Important Quirks), and the fix is therefore two _opt-in_ chimes rather than an unconditional cue. `focusEndSoundEnabled` / `breakEndSoundEnabled` gate a new `maybeChimeAtCrossing()` that runs in the `if (autoStart)` branch's **else** position, inside the existing `prev > 0` guard — so it fires exactly once per crossing and **changes nothing else**: no logging, no mode switch, no `clearLoop`, overtime byte-identical to 0.6.2. The chime _announces_ the end; it does not end anything. **The settings are INDEPENDENT of auto-start, and that was a second-round correction worth recording.** The first cut hid each chime row while its auto-start was on, on the reasoning that the auto-start path always chimes anyway — and the user's objection was that a control vanishing because you turned something _on_ reads backwards. It did, and the hiding was a symptom: the two booleans encoded only **three** states, because auto-start did not merely make the chime irrelevant, it silently **overruled** it, so "start the next session quietly" was unreachable. `completeNaturally()` now consults the same `endChimeWanted()` as the crossing, which makes all four states real, deletes the dependency, and let the whole visibility mechanism (`SettingRowSpec.visible`, the 1.13 `visible` forward, the pre-1.13 heading filter) come back out — dead weight once nothing is conditional. **The migration is what makes that safe:** `deriveEndChimes(read, loaded)` in [settingsStore.ts](settingsStore.ts) seeds each chime from the matching AUTO-START value on upgrade, because before 0.6.3 auto-start chimed unconditionally and overtime never did, so that toggle exactly describes what the user hears today — nobody's sounds change, and everyone gains a working switch. A fresh install instead gets break-end on and focus-end off (focus→break is the edge that would interrupt a session someone may want to continue); `"damaged"` lands on the defaults and stays silent. `DEFAULT_SETTINGS` holds **false** for both because it is also the `Object.assign` merge base for an upgrading user. **The one real trap was the second cue:** with a chime on, Stop or Skip in overtime rang the same sound again seconds later, so `endCueSounded` suppresses it — and the flag must record an **audible event, not an intent**, because `soundEnabled` is the master gate _inside_ `playSound` and can be flipped between the crossing and the Stop, at which point "it already rang" is a lie that silences a Stop which has rung since 0.2.1. It is therefore stamped only `if (settings.soundEnabled)`, and cleared in `switchMode`, **`reset()` and `addMinutes()`** — the last two because both are reachable in overtime and put time back on the clock, after which a second crossing's Stop would otherwise be silent. All three were measured as real holes before the fix and each has its own test. The `remainingMs > 0` arm of `shouldPlayManualEndCue` is **insurance, not the rule** — a mutation run confirmed `>= 0` kills no test, and the comment says so rather than claiming a hazard that does not exist. **Stop and Skip stay unconditional** (beyond that guard): they are a deliberate button press, and the chime settings speak about the clock running out. The three copies of "bell or ding?" collapse into one `playEndCue()`. **UI:** the panel's flat "Auto-start" section becomes two event-keyed sections (**When focus ends** / **When a break ends**), each pairing its chime with its start toggle; the **auto-start toggles also moved into the settings tab** (new **Audio** group), so all four rows are reachable from either surface. **Independence bought a second clarity problem, and it needed copy rather than a cleverer label:** "Play a chime" carries no scope, so under a heading naming an event a reader can fairly take it to mean "…if the timer just sits there" — leaving "does it still chime when the break auto-starts?" answerable only by experiment. The chime therefore sits ABOVE its start toggle (reading order presents it as a property of the whole event rather than a fallback), and each pair closes with a `.gp-settings-hint` line from new pure [sessionEndSummary.ts](sessionEndSummary.ts) stating the outcome for the combination currently set — all four per edge, each distinct, each under 40 chars for the 260px column. It takes the **settings object, not two pre-resolved booleans**, which is the load-bearing part: a mutation run proved the edge→field mapping uncovered while it lived in the view (nothing can import GentlePomoView), and moving it inside the tested function killed both mutants. Note the deliberate crossing it now owns — the FOCUS edge is governed by `autoStartBreak`, because what starts when focus ends is the break. `renderSettingsPanel` seeds the lines by calling `syncSettingsPanel()` directly rather than waiting for an emit: the rows are built empty and the tick does not run while the timer is idle, which is exactly when someone opens the gear panel to read what these toggles do. **The settings tab shows the same line, and there it had to be a `render` row rather than a `desc` string** — a correction to an earlier reading of the API. `getSettingDefinitions()` is documented as "called on every `display()`", so a computed description IS fresh whenever the tab is opened; but `refreshDomState()`, the only thing Obsidian runs after `setControlValue`, says outright "toggles CSS state in place, **no re-render**" and re-evaluates nothing but `visible`/`disabled`. A static string would therefore sit contradicting the toggle just flipped, and the fix cannot be `update()` (1.13-only, `no-unsupported-api`). So `endSummaryRow()` keeps the created node in `endSummaryEls` and `refreshEndSummaries()` rewrites it from the four `setControlValue` cases; its `name`/`desc` are empty so both render paths describe the row identically and the drift test still holds. Its rows carry `gp-setting-summary`, which is also how the "every row renders something" test exempts them — deliberately, since they are text rather than a control. **Auto-start labels were reworded** on the user's request to **Auto-start the break** / **Auto-start the focus** — "Start the break" read as though it might begin one immediately. They are now identical on both surfaces, so they live as two consts in [sessionEndSummary.ts](sessionEndSummary.ts) and are imported by each: shared because they are identical, and identical because each says what it does without needing context from around it. **0.6.2 adds the third theme, Pixel City (working name Rooftop Skyline), in pixel art** — the first theme made of pictures rather than CSS, which is what 0.6.0's theme independence and 0.6.1's ink slots and scrim were built for. **The art was neither drawn from a sketch nor generated by an image model**: the user tried Retro Diffusion and rejected the quality, so the plates are produced by a script — [art/pixel-city/pixlib.py](art/pixel-city/pixlib.py), a strict palette-indexed toolkit (Endesga 32, ordered Bayer dither, indexed-PNG output; nothing in it can emit an off-palette or anti-aliased pixel) and [art/pixel-city/skyline.py](art/pixel-city/skyline.py), the design as numbers. **Generate many, pick one** was the process: six candidate skylines fanned out with distinct art directions and ranked by a three-lens judge panel, the user merged two (Soft Dusk's buildings and cat, Lofi Cozy's 2×2 window grid and sky colours, no billboards), then asked for three things in turn, each a number in the script. The pale sky bands moved **below the clock text** (`SKY_KEYS`: nothing lighter than mid-tone above row 92 of 128 — the first cut put a cyan haze at row 77, straight behind the end-time line, and white on that cyan is invisible). **More in-between states**: 5 → 8 sky plates with designed late-day / golden-hour / twilight ramps, because an opacity blend of blue and magenta passes through a grey nobody chose while a designed plate keeps its saturation, and 3 → 6 window waves, each easing on over 1% of the session rather than switching. **Two planes of buildings, a little shorter**: a slate far row behind the ink near row — navy was tried first and vanished into the navy night sky leaving its windows floating; slate reads as distance by day and as a lit haze by night — in the "downtown behind" arrangement chosen from four generated layouts via `skyline.py --layout`. **Delivery is the only part with a trap**: Obsidian installs exactly three files and manifest.json cannot declare more, so a loose image works on the dev machine and is silently missing for every catalog user, and no local test can find that. The sixteen 128×128 plates (under 7 KB — the first cut shipped 17 KB because pixlib padded every palette to 256 entries, 60% of each file zeros) are therefore `import`ed in [pixelCityArt.ts](pixelCityArt.ts) and inlined by `@rollup/plugin-url` (`rollup.config.mjs` now includes `**/*.png`; `audio-modules.d.ts` declares the module), the route the three mp3s already take — main.js 729,442 → 741,880 (756,196 before the palette padding was found). **0.6.1 is the visible half of 0.6.0's design system**, and the release where its structure got its first real test: every change below lands in a theme block or a token, and **not one shared rule had to move**. **The day/night badge was a whole phase behind the artwork** — `getDayNightIcon` lived in the view and branched on raw `remainingMs` at **halves**, while the square was driven by `skyPhase` in a different block of the same file, so focus showed a sun for the entire first half, sunset for the second, and **moon only once `remainingMs <= 0`**: across a whole normal session the badge never reached night while the artwork faded all the way there, and break mirrored it. Three properties fall out of putting the switch in the ramp's completion callback: a ⏸/⏹ landing inside the fade **cancels the advance and wins** (`cancelMusicRamps` drops the callback), `armMusicFadeIn` takes its **still-running** branch because the player was never halted (so it ramps up from `musicRampLevel`, which the fade-out left at 0, and its `holdWhile` spends the rise on audio rather than on the buffering gap), and a **no-op advance** — last item, no loop, bogus `list=` — degrades to a dip-and-swell rather than to silence, because that branch never waits on a transition that will not come. It clears `pendingResumeSeconds`/`resumeSeekLanding` **on the landing, not the click** (a seek posted for the outgoing item blocks `trackMusicPosition` until the new item's clock passes the old offset; clearing on the landing means a cancelled advance leaves the outgoing item's bookkeeping untouched) but **deliberately NOT `musicCurrentDuration`/`musicCurrentVideoId`**: `duration` rides only the fuller state-change payloads, and a no-op advance produces no state change, so a nulled duration would never be restored and `isResumablePosition` reads null as "live stream" — 0.5.4 trap 5 verbatim. **(4+5) One oEmbed probe per pasted link** drives both the inline error and the name prefill. The prefill takes the **title**, with the channel as fallback (of this vault's three links one title is a lone ZWJ, i.e. invisible, so the fallback is not theoretical), then `normalizeNameCase`: an all-caps title is sentence-cased and a lowercase opening is capitalised, but a mixed-case first word (`iPhone`) is left alone. Staleness follows 0.5.6's provenance rule: the URL is **frozen at issue time** and compared on landing, a per-slot token drops superseded answers, and `hide()` bumps every token. The prefill is an **offer, never an overwrite** — it needs the stored name empty, the visible box empty, the caret elsewhere, and the box still connected, because a trimmed setting reads empty while the user has their cursor in it. **0.5.6 fixed:** three defects in the remembered-music-position feature, all found by auditing "what if the user edits the URL while the previous one is paused rather than stopped?" **(1) The plugin still emitted `start=`** — not for the resume offset (0.5.3 moved that to a seek precisely because a `start=` embed, alongside the loop feature's `loop=1&playlist=<self>`, stops responding to `playVideo` after a `pauseVideo` and recovers only on `stopVideo`), but for the **user's own pasted `t=`**: `parseYouTubeUrl` → `target.startSeconds` → `buildEmbedUrl` set the param, so anyone pasting YouTube's "copy link at current time" got a player that went permanently silent on ▶️→⏸→▶️. `buildEmbedUrl` now **never** writes `start=` for any offset from any source (test-locked across `90 / 0 / null`), and `planResume` returns the URL's own `t=` as its **fallback** `seekSeconds` — deliberately with **no `MUSIC_RESUME_MIN_SECONDS` floor** (that floor exists to stop a barely-started track being "resumed"; a pasted `t=3` is an explicit instruction). Now that a pasted offset actually reaches playback, `parseYouTubeUrl` also reads the **legacy `#t=` fragment** form (`youtu.be/<id>#t=1m30s`) — such links parsed fine before but their timestamp was silently dropped. The hash is parsed as a query string (so `#t=90&…` works) and consulted **last**: an explicit `start=`/`t=` param is the modern share format and wins, and a fragment carrying no `t=` yields null rather than throwing. **(2) A stored position outlived the URL it came from.** It was keyed by video + playlist context only, so two deliberate edits were silently overridden — a switch to a different item of the **same playlist** (planResume's "inside a list the saved video wins" rule, correct for reopening an unchanged URL, hijacked the pasted item) and a changed `t=` on the same video (the stored offset beat it) — both **sticky**, since every later rebuild re-planned from the same store, and unrecoverable without ⏹ _plus_ closing the panel. **0.5.4 added:** the music **fades in and out** on ▶️/⏸/⏹ instead of snapping (user request: make the audio change sound smoother). Shape: ▶️ parks the embed at `setVolume(0)`, posts `playVideo`, and **arms** the fade — the ramp only runs on the first PLAYING transition, because `playVideo` is followed by a buffering gap with no audio in it and a fade spent on silence is a fade nobody hears; ⏸/⏹ ramp **down to silence first and post `pauseVideo`/`stopVideo` on the landing** (posting it up front cuts the audio dead and leaves the fade nothing to fade). New pure `buildFadeRamp` in [youtubeMusic.ts](youtubeMusic.ts) beside `buildVolumeRamp`: identical contract (excludes `from`, lands exactly on `to`) but **quadratically weighted toward the quiet end** — loudness is perceived roughly logarithmically, so a linear amplitude ramp spends half its time inside the top 6 dB and sounds like the music snaps in and then hangs; the eased ramp sits a quarter of the way up from the quiet end at the halfway point, and a fade-out is the exact mirror of the fade-in that undoes it. **Ducking keeps the linear `buildVolumeRamp`** — it moves between two audible levels, where the curve would only make the dip feel late. Constants ([constants.ts](constants.ts)): `MUSIC_FADE_IN_MS` 800 / `MUSIC_FADE_OUT_MS` 450 (asymmetric for the duck's own reason — the out-fade _delays the pause_, so it must stay short enough that the button feels immediate) / `MUSIC_FADE_STEP_MS` 50 / `MUSIC_FADE_ARM_TIMEOUT_MS` 5000 / `MUSIC_FADE_HOLD_MAX_MS` 3000.

**Ducking and fading share ONE ramp channel**, so they can never post over each other: `duckRampInterval`/`duckLevel`/`runDuckRamp`/`cancelMusicDuck` became `musicRampInterval`/`musicRampLevel`/`runMusicRamp`/`cancelMusicRamps`, and `runMusicRamp(levels, stepMs, onDone?, holdWhile?)` takes a **prebuilt level array plus an explicit `stepMs`** — the first cut defaulted `stepMs` and silently ran the duck's down-ramp at the fade's 50ms cadence, shortening a 240ms dip to 200ms, so the step count and the cadence must always travel together. `musicFadePhase` (`"armed" | "in" | "out" | null`) is the fade's state; a pending `pauseVideo`/`stopVideo` lives in the ramp's completion callback, so **replacing or clearing the ramp is what cancels the command**.

**Seven traps this feature is built around** (all found by adversarial review before shipping; re-introducing any of them is a silent-music or lost-position bug):

1. **⏸ → ▶️ inside the fade-out must not arm.** Cancelling the ramp drops the pending `pauseVideo`, so the player _never stopped_: `playVideo` is a no-op, no `onStateChange` follows, and the ~4Hz `infoDelivery` repeats are filtered out by `handleMusicState`'s `state !== musicPlayerState` guard. An armed fade would wait forever with the volume parked at 0 — and since `postMusicVolume` early-returns while a fade is in flight, the volume control would go dead with it. `armMusicFadeIn` reads `musicPlayerState` **before** clearing and, when the player is still running (PLAYING _or_ BUFFERING — a rebuffer mid-fade-out is the same trap), eases straight back up from the abandoned level instead of arming.
2. **A dropped `playVideo` must not strand the arm** (iOS refusing a first play, a dead video): `MUSIC_FADE_ARM_TIMEOUT_MS` stands the fade down and re-posts the user's volume — inaudible, since nothing is playing, and it hands the volume control back. If the player is merely **buffering slowly** when the backstop fires it hands over to `beginMusicFadeIn` instead of cancelling, because the ramp holds itself until audio starts (trap 3) — cancelling there would make a slow connection snap in at full volume, which is the one thing this feature exists to stop. `postMusicVolume`'s skip path deliberately **does not stamp** `lastAppliedMusicVolume`, so `applySettings`' convergence check keeps retrying and heals the moment any fade ends.
3. **The 0.5.3 resume seek rebuffers**, and the fade-in starts on the very PLAYING transition that posts the `seekTo`. `runMusicRamp`'s `holdWhile` predicate (fade-in only) skips ticks while the player isn't PLAYING, so the ramp waits the rebuffer out instead of running through the silence and arriving at full volume. Bounded by `MUSIC_FADE_HOLD_MAX_MS` so a player that never returns can't strand it half-way up.
4. **A cue during a fade-in must still duck.** "Press ▶️, then press Start" puts the war drum squarely in the fade window, and blocking the duck there would leave a cue playing over music rising to full volume — precisely what ducking exists to prevent. `duckMusic` therefore **takes the volume over** during `"armed"`/`"in"` (clearing `musicFadePhase`, because the abandoned fade's landing callback dies with the replaced ramp) and its restore ramp finishes the rise. A fade-**out** still wins: the player is about to pause, so there is nothing to duck.
5. **⏹ Stop has to stay atomic.** Its `stopVideo` now rides in the ramp's landing callback, which a ▶️ press cancels — so **every** part of Stop moved into that callback with it (`clearMusicPosition`, `pendingResumeSeconds`, `resumeSeekLanding`, `musicCurrentDuration`). The first cut cleared them on the click, and an aborted Stop then left `musicCurrentDuration` null forever, which `isResumablePosition` reads as "live stream" — position recording silently dead for the rest of the track. Only `musicStopPending` is set on the click (it blocks `trackMusicPosition` while the fade still plays audio, so those last seconds can't re-bank the position Stop is about to drop). **The flag's lifecycle is exactly the straggler window**: `armMusicFadeIn` clears it (aborted Stop), and a _landed_ stop is **settled** — flag down — on the first non-audible transition afterwards (or at the landing itself when the player was already halted, since no further transition may come). Leaving it up past that point was itself a lost-position bug: trap 7's resume path never passes through ▶️, so a stuck flag killed recording for the whole resumed session. While the flag is up, `applySettings`' rebuild path **plans resume against an empty store** (a Loop flip inside the 450ms window would otherwise snapshot the position the stop is mid-way through forgetting and seed the new iframe with it), and `destroyMusicIframe` **honours the pending stop** — `clearMusicPosition()` instead of `flushMusicPosition()`. (`resumeSeekLanding` was already leaking in 0.5.3's Stop handler; this is where it got fixed.)
6. **A volume change during a fade-in must win immediately** (0.5.0's promise). The ramp snapshots its target at build time, so `postMusicVolume` **re-aims** a `"in"` fade by rebuilding it from the current level — and, uniquely on that path, **does** stamp `lastAppliedMusicVolume`: leaving it stale there would have `applySettings`' ~20Hz check rebuild the ramp every tick, restarting it faster than a single step could fire. The no-stamp rule in trap 2 applies only to the phases that don't act on the value — and `duckMusic` **stamps the setting when it takes a fade over** (trap 4), because inheriting a stale stamp there would have the next 50ms tick cancel the duck it just started.
7. **A landed ⏸/⏹ parks the embed at volume 0, and playback can resume without ▶️.** Hardware media keys drive a YouTube embed in Electron; in 0.5.3 pause kept the user volume so a media-key resume was audible — silent playback with ⏸ showing would be the regression. `handleMusicState` detects the orphaned park (transition into an audible state **from a halted one**, no fade phase, no ramp timers, `musicRampLevel` still non-null) and fades up from the parked level — re-arming instead when the edge is BUFFERING, so the fade isn't spent on silence. The **from-a-halted-state** condition is load-bearing: a straggler PLAYING that races the just-posted `pauseVideo`/`stopVideo` arrives from a still-audible previous state and must not trigger it. Related: the `"armed"` stand-down fires **only on PAUSED/ENDED** — the embed emits transient UNSTARTED/CUED on its way to playing, and treating those as dead ends cancelled the fade and let the music snap in (the arm timeout covers a player that truly never starts).

Also: `maybeNotifyMusicEnded` is suppressed while `musicFadePhase === "out"`, since a track ending inside the fade would answer the button press with "the music ended — paste a new link"; `setMusicButtonsPlaying` is split out of `updateMusicButtons` so a fade-out can swap the ▶️/⏸ buttons **immediately** (waiting a fade-length for YouTube to confirm leaves the button looking dead) **without** touching `musicPlayerState`, which the flush / resume-seek / notice logic still reads as the real previous state — and `updateMusicButtons` lets an in-flight fade-out win, so a rebuffer or playlist advance can't put ⏸ back moments after it was pressed. `fadeMusicOut` skips the ramp entirely unless the player is actually running, so ⏹ on an idle player still forgets instantly. No settings, no schema change, no new network surface; `buildFadeRamp` is node-tested in [tests/youtubeMusic.test.ts](tests/youtubeMusic.test.ts).

**0.5.3 added:** the lofi player **remembers where it was** and reopens there (user decision: **restore the position, never auto-play** — Obsidian startup must not burst into music, and iOS blocks first-play without an in-iframe tap, which the hidden player has none of). Capture: `parsePlayerMessage` in [youtubeMusic.ts](youtubeMusic.ts) no longer throws away everything but `playerState` — `infoDelivery` now decodes to a new `{type:"info", state, currentTime, duration, videoId}` variant (every field nullable; the stream sends them piecemeal, never all at once), which is the ONLY way to read the clock (the postMessage protocol has no request/response getters — the JS API's getters just read a cache fed by this same stream). Storage: internal state fields `lastMusicVideoId`/`lastMusicPlaylistId`/`lastMusicSeconds` in [types.ts](types.ts) beside `lastGoalHitDate`, plus the user-facing `musicResume` toggle (default `true`, Music group in **both** settings-tab paths, desc shared via `MUSIC_RESUME_DESC`). The plugin owns persistence (`recordMusicPosition` / `clearMusicPosition` / `flushMusicPosition` / `musicResumeState` in [main.ts](main.ts)); the view owns the running picture. **Write amplification was the design constraint** — data.json lives in the vault, so every save is sync traffic: the ~4Hz stream only mutates in-memory fields (deduped to whole seconds, so ~1 update/sec, no disk), and the _save_ happens on boundaries — PAUSED, ⏹ Stop, ENDED, `destroyMusicIframe` (panel close / leaf move / URL change), `onunload` — with a dirty-flag-gated `MUSIC_POSITION_SAVE_MS` (60s, [constants.ts](constants.ts)) `registerInterval` as the force-quit backstop (worst case ≤60s of drift; a quiet beat is one boolean check).

**Restore does NOT touch the embed URL — this is the load-bearing part.** The first cut of 0.5.3 folded the offset in as `start=`, and it broke playback (user-reported): an embed loaded with `start=` — alongside the loop feature's `loop=1&playlist=<self>` — **stops responding to `playVideo` after a `pauseVideo`**, recovering only on `stopVideo`. (Ruled out plugin-side: nothing gates `playVideo` but `musicPlayerReady`, which only `destroyMusicIframe` clears, and pause never calls it. Also not a resumed-past-the-end case — the reporter's video was 2h22m and the offset 129s.) So pure `planResume(target, saved)` returns a `{target, seekSeconds}` plan whose target is **byte-identical to what 0.5.2 built** (returned by _reference_ when the video is unchanged), and the offset rides as a one-shot `seekTo` posted from `handleMusicState` on the first PLAYING/BUFFERING transition — the only state YouTube documents as safe to seek from (from a _cued_ player `seekTo` starts playback, i.e. exactly the auto-play this feature must not do). Consuming it on BUFFERING usually lands the jump before any audio. Everything about playback, looping, ⏹ Stop and close-the-panel-to-stop therefore behaves exactly as in 0.5.2, and the earlier `musicSeekToZeroOnPlay` hack (which existed only to undo a `start=` that YouTube re-applies on every loop repeat) is gone. The plan is read **at iframe-build time only, deliberately NOT part of `lastMusicKey`** — keying on a value that moves every second would rebuild the iframe ~20×/sec (the iPhone-flicker regression family). A posted seek sets `resumeSeekLanding`, and `trackMusicPosition` ignores clock readings below it until it lands, so the pre-seek `currentTime: ~0` can't overwrite the position being resumed to (if the seek is never honoured nothing is recorded, leaving the stored position intact for next time).

**Resume is keyed by video ID, not playlist index** (`index=` is 1-based while `infoDelivery.playlistIndex` is 0-based, and an index breaks when the playlist is reordered): a playlist _item_ still has to come from the URL, since a seek can't cross items, so `planResume` swaps `target.videoId` for the saved one — `/embed/<id>?list=<list>`, the shape a watch+list URL already produced in 0.5.0. The list context must match exactly, so a changed URL never inherits an offset. Guards, split by side: `isResumablePosition` (record side) drops the last `MUSIC_RESUME_END_MARGIN_SECONDS` (10s) of a track and anything with a non-positive `duration` — **which is how a live stream reports, so streams never store an offset**; `planResume` (apply side) drops anything under `MUSIC_RESUME_MIN_SECONDS` (5s). The floor lives on the apply side _on purpose_: recording the opening seconds is what lets a restarted/looped track immediately overwrite a stale offset. **⏹ Stop = forget** (user's own framing — pause remembers, stop forgets; it doubles as the manual "start from the top" control with no new UI), dropping both the stored position and any pending seek; ENDED clears too. New pure helpers are node-tested in [tests/youtubeMusic.test.ts](tests/youtubeMusic.test.ts), including a regression test asserting the built URL contains no `start=`. No migration (the `Object.assign` merge covers the new fields), no new network surface, no README **Network use** change.

## Architecture

State flows through a listener pattern:

```
GentlePomoPlugin (main.ts)
    │
    ├── TimerEngine ──emit(TimerState)──▶ GentlePomoView   (renders the visual timer)
    │                                  │      └── MusicController  (music state machine; I/O via MusicHost)
    │                                  └▶ status bar in main.ts
    │
    ├── LogManager          (appends daily-log markdown lines, TTL cache for today's totals)
    ├── FocusTotalTracker   (focusTotals.ts — today's logged total: TTL + day stamp)
    ├── MusicStationStore   (musicStationStore.ts — the 3 slots and their remembered positions)
    ├── SettingsStore       (settingsStore.ts — data.json, with the failures left visible)
    └── GentlePomoSettingTab  (Obsidian PluginSettingTab)
```

- `TimerEngine` is the single source of truth for timer state. Every subscriber gets a fresh snapshot via `onChange`.
- The view does **not** own state — it reads from `TimerEngine` and dispatches user actions back to it.
- Persistence goes through [settingsStore.ts](settingsStore.ts), **not** `Plugin.saveData()` — see Important Quirks for why that method cannot report a failure. Defaults are merged from `DEFAULT_SETTINGS` in [constants.ts](constants.ts).
- **The extracted modules take their host as an interface of calls, never captured references** (`MusicHost`, `FocusTotalHost`, `MusicStationStoreHost`, `SettingsIo`): `loadSettings()` replaces the settings object wholesale, so a reference snapshotted at construction would read the pre-load one forever.

## Conventions

- **State updates flow through `TimerEngine.emit()`** → listeners. Never mutate `TimerState` from the View or status bar.
- **Defaults live in [constants.ts](constants.ts)** `DEFAULT_SETTINGS`. New settings must be added there and merged via `Object.assign` in `loadSettings()` ([main.ts](main.ts) `loadSettings`).
- **Task IDs** are detected via the `🆔` emoji marker. Log entries use Obsidian wiki-link syntax: `[[path|display name]]`.
- **CSS classes are `gp-*` prefixed.** Stay consistent — search [styles.css](styles.css) before inventing new names.
- **Read [DESIGN.md](DESIGN.md) before editing [styles.css](styles.css).** It holds the token layers, the artwork-vs-chrome rule, and a ten-entry "do not break" register — every entry is something an ordinary tidy-up would do, and each one breaks something silently (source-order ties, double-class variants that carry a specificity win, five platform workarounds that read as dead code).
- **Logging:** use `logger.warn/error/debug` from [logger.ts](logger.ts), not raw `console.*`. The prefix `[GentlePomo]` is added automatically.
- **Audio assets** (`ding-sound.mp3`, `singing_bell_short.mp3`, `war-drum_short.mp3`) live at the project root and are loaded by relative path from [TimerEngine.ts](TimerEngine.ts).
- **Task parsing** must go through [taskLoader.ts](taskLoader.ts) (`loadTasks`, `groupTasksByDate`, `normalizeTaskText`, etc.) — never re-implement regex inline.

## Settings & Persistence

`GentlePomoSettings` in [types.ts](types.ts) is the schema. Stored by Obsidian in `data.json` at the project root. Modify via `plugin.settings.foo = ...` then `await plugin.saveSettings()`.

## Log Format

Daily file: `<folder>/YYYY-MM-DD-gentle-pomodoro-log.md`. One line per session, inline-field format so Dataview can query it:

```markdown
- 🍅 Focus | Task:: [[Projects/MyProject.md|Write Docs]] | ID:: abcd12 | Start:: 2025-12-23 10:00:00 | End:: 2025-12-23 10:25:00 | Scheduled:: 1500 | Pauses:: [] | Total:: 1500 | Status:: finished | Type:: focus
- ☕ Rest | Start:: 2025-12-23 10:25:00 | End:: 2025-12-23 10:30:00 | Scheduled:: 300 | Total:: 300 | Type:: short-break
- ☕ Rest | Start:: 2025-12-23 11:00:00 | End:: 2025-12-23 11:15:00 | Scheduled:: 900 | Total:: 900 | Type:: long-break
```

`Type::` was added in 0.1.0 — values are `focus | short-break | long-break`. Additive; existing Dataview queries still match.

Field order is **load-bearing** for users' Dataview queries — do not reorder or rename without a version bump and changelog note. The schema is locked in by [tests/logManager.test.ts](tests/logManager.test.ts).

## Important Quirks

- **`obsidian` dep is pinned to `^1.13.1`** (types-only npm package; 1.13 typings are required for the declarative settings API — `getSettingDefinitions()` in [GentlePomoSettingTab.ts](GentlePomoSettingTab.ts), with a generic `display()` as the pre-1.13 fallback — since 0.5.8 **both render from the same `settingGroups()` list**, so there is nothing left to keep in sync). [package.json](package.json) and [manifest.json](manifest.json) track 0.6.4; `minAppVersion` is **1.7.2** (raised from 1.0.0 for `Workspace.revealLeaf` / `Vault.createFolder`, which `eslint-plugin-obsidianmd`'s `no-unsupported-api` rule gates). [versions.json](versions.json) maps each plugin version to its `minAppVersion`.
- **The silent zero crossing is DELIBERATE — do not "fix" it into an unconditional cue.** When a session's countdown reaches zero the timer plays nothing and slides into overtime; the end-of-session cue fires only when the next mode's auto-start toggle is on. This reads exactly like a bug (GitHub issue #5 reported it as one) and is not: **protecting flow state is a product value here**, on a level with the deliberately hidden countdown. A chime at minute 25 is precisely the interruption this plugin exists to avoid. 0.6.3 makes the cue _available_ through two opt-in toggles; it did not make it unconditional, and the focus→break edge — the flow-breaking one — still defaults to silence. Any future sound work must stay opt-in, and must not change overtime (no logging at zero, no mode switch, no `clearLoop`).
- **Audio lifecycle:** [TimerEngine.ts](TimerEngine.ts) owns a single shared `AudioContext`, created lazily in `playSound()` and resumed if suspended; decoded clips are cached in `audioBuffers`. `TimerEngine.dispose()` (called from [main.ts](main.ts) `onunload`) closes the context and clears the tick loop — Chromium caps live `AudioContext`s, so it must not leak across disable/enable cycles.
- **The music embed never requests a YouTube playback quality — audited (pre-0.5.7), correct as-is, don't "fix" it.** Nothing in [youtubeMusic.ts](youtubeMusic.ts) sets one (`PlayerCommandFunc` has no `setPlaybackQuality`; `buildEmbedUrl` writes no quality param), and nothing could: the IFrame API's quality setters (`setPlaybackQuality`, the queueing functions' `suggestedQuality` arg) are documented no-ops — the player picks automatically from size + bandwidth, so the 1×1 `.gp-music-player` gets the lowest video rendition. That is the optimum for an audio-only player: audio rides a separate adaptive stream whose quality (~128–160 kbps) is identical at 144p and 1080p, so the one lever that still exists — letting the hidden iframe report a large size — would stream and decode invisible pixels for zero audible gain. The sole case where the video tier touches audio is muxed live-HLS variants (~48 kbps audio at the bottom tiers), which is native-HLS playback, i.e. iOS — where the feature cannot play at all (error 153); desktop Electron plays via MSE with a separate audio track. `parsePlayerMessage` deliberately discards quality-only `infoDelivery` payloads (they are in the stream if a runtime check is ever wanted).
- **`Plugin.saveData()` and `Plugin.loadData()` swallow every error — never wrap them in a try/catch.** Both are declared `Promise<any>` and neither can reject. `saveData` → `vault.writePluginData` → `Vault.writeJson`, whose catch body is **empty**: a failed write resolves `undefined`. `loadData` → `readPluginData` → `Vault.readJson`, which catches too and returns **`null` only for ENOENT** and **`undefined` for a parse failure or an unreadable file** — a tri-state the typings do not express. Both verified by reading `obsidian-1.13.7.asar` and confirmed identical in the 1.7-era build. Consequences, all of which 0.5.8 shipped wrong on the first attempt: a `try`/`catch` around either is unreachable dead code; a damaged data.json produces a _silent_ fall back to defaults, not a crash; and the only way to detect it is `loaded === undefined`. Writes therefore go through `vault.adapter.write` ([main.ts](main.ts) `writePluginData`), which does reject — the same reason LogManager reaches for the adapter. See [settingsStore.ts](settingsStore.ts) and [tests/settingsStore.test.ts](tests/settingsStore.test.ts).
- **`main.js` is the built artifact.** It's gitignored, but Obsidian loads it directly — you must `npm run build` (or have `npm run dev` running) before reloading the plugin.
- **Images reach users only from inside `main.js`.** Obsidian installs exactly `manifest.json`, `main.js` and `styles.css`, and `manifest.json` has no field to declare more — a loose image in the plugin folder works on the machine that put it there and is silently missing for every catalog install, which no local test can detect. The Pixel City plates are therefore `import`ed ([pixelCityArt.ts](pixelCityArt.ts)) and inlined by `@rollup/plugin-url` like the three mp3s (`include: ["**/*.mp3", "**/*.png"]`, `limit: Infinity`). Keep raster art indexed and at source resolution; [tests/pixelCityArt.test.ts](tests/pixelCityArt.test.ts) checks the colour type and budgets the bytes. `Vault.adapter.getResourcePath` is API-legal but can only address a file that is never there — keep it for a future "user picks their own image" feature.
- **iPad icon sizing needs a CSS `min-width` floor.** WebKit/Safari collapses an SVG flex item's main-axis (width) to ~min-content (~8px) while honoring height, so the control glyphs render as thin slivers — and a plain CSS `width` (even `!important`) does **not** fix it. The fix is a `min-width`/`min-height` floor (+ `flex-shrink: 0`) on `body.is-mobile/.is-tablet .gp-icon-btn svg.svg-icon` in [styles.css](styles.css); the `min-*` floor is the load-bearing part (the flex algorithm can't shrink below it), so don't drop it. It **must** be CSS, not inline `el.style.setProperty` — `eslint-plugin-obsidianmd`'s `no-static-styles-assignment` forbids inline style assignment (and disabling that rule). (Diagnosed device-side via Safari Web Inspector; desktop/iPhone were never affected.)
- **Auto-open** runs inside `this.app.workspace.onLayoutReady()`. A `MutationObserver` fallback waits for any settings/community-plugin modal to close before activating the view (handles freshly-installed-plugin UX).
- **`noImplicitOverride: true`** is enabled in [tsconfig.json](tsconfig.json). Always mark methods that override Obsidian base classes (`Plugin.onload`, `ItemView.onClose`, etc.) with `override`.
- **`package-lock.json` is tracked** — CI uses `npm ci` for reproducible builds (since 0.1.1). Regenerate with `npm install` whenever `package.json` changes.
- **Local-timezone date string** used for daily reset logic is `moment().format("YYYY-MM-DD")` (defined as `todayLocalStr()` in both [main.ts](main.ts) and [TimerEngine.ts](TimerEngine.ts)). Same format as the daily log file naming, so all "today" logic agrees.
- **Per-task counter is opt-in** (`incrementPomodoroCountOnFinish`, default off). When enabled, finishing a focus session linked to a task increments a lifetime `🍅 N` marker on the task line. The marker sits at the **end of the description, before the Tasks emoji fields** (since 0.5.1 — a trailing marker breaks Tasks date parsing, see issue #2) and before any trailing `^block-id`. Legacy `🍅 N (YYYY-MM-DD)` markers from an earlier 0.1.0 build are still readable; on the next increment the parens are stripped, the marker becomes `🍅 N+1`, and a misplaced (≤0.5.0 trailing) marker is relocated in front of the fields.
- **Internal state fields** in `GentlePomoSettings` (`lastGoalHitDate`, `sessionsSinceLongBreak`, `sessionCounterDate`) are persisted to `data.json` alongside user settings but are not surfaced in any settings UI — they implement the once-per-day notice and long-break counter.
- **The music state machine's rules are rules about statement order, and its tests are mutation-checked.** Every music defect this plugin has shipped was "read this field _before_ clearing that timer" or "post the command on the ramp's landing, not up front" — which is why [MusicController.ts](MusicController.ts) takes its I/O injected and its tests drive a fake clock. **Extracting pure predicates would not have caught a single one of them.** Treat the comment above a statement there as describing a bug that shipped, and re-run [tests/musicController.test.ts](tests/musicController.test.ts) after touching it — but note a passing suite is only evidence if the test can fail: 0.5.8 found six tests there asserting something weaker than their name said (one never entered `handleState`'s transition block at all, one was masked by the stall rate limit, one could not observe the ordering it was named after). Break the rule on purpose and watch the test go red before trusting it.

## Don't Do This

- Don't add `setInterval` calls in the view — subscribe to `TimerEngine.onChange` instead.
- Don't touch the DOM from `TimerEngine` or `LogManager` — UI rendering belongs in the View.
- Don't reach into `this.app.metadataCache` for task parsing — use [taskLoader.ts](taskLoader.ts).
- Don't use `console.*` directly — go through [logger.ts](logger.ts) (and `console.log` is lint-blocked anyway).
- Don't reorder or rename inline fields in log lines — tests in [tests/logManager.test.ts](tests/logManager.test.ts) will fail, and users have Dataview queries pinned to the current schema.

## Reusable Patterns

- **Listener pattern:** `onChange/offChange/emit` in [TimerEngine.ts](TimerEngine.ts) — copy this shape for any new subscribable state.
- **Settings merge:** `Object.assign({}, DEFAULT_SETTINGS, loaded ?? {})` in [main.ts](main.ts) `loadSettings`.
- **TTL cache:** `FOCUS_TOTAL_CACHE_TTL_MS` + `lastFetchMs` + `inFlight` + a `baseDate` day stamp in [focusTotals.ts](focusTotals.ts) `FocusTotalTracker.refresh()` ([main.ts](main.ts) `maybeRefreshFocusTotal` just delegates), and the simpler `focusTotalCacheAt` / `focusTotalCacheDate` pair in [logManager.ts](logManager.ts) `getTodayFocusSeconds` — reuse for any expensive periodic fetch. The day stamp, not the TTL, is what stops a stale value surviving local midnight.
